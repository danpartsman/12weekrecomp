# External Connections module

Provider protocol adapters live in `src/WebRecomp.ExternalConnections`, an independent .NET class library with no dependency on the fitness engine, web UI, or database. Fitdays is the first adapter. Host orchestration, encrypted storage, background scheduling, and measurement mapping live together under `WebRecomp.Web/Services/ExternalConnections`. Future providers need their own adapter and mapping; supported provider settings are maintained through Administration without editing code.

Routes: `/ExternalConnections` (Profile → Device integrations), `/Fitdays` (connect, preview and select scale profile), `/AdminExternalConnections` (Administration → External connections). The supported module is enabled on `recomp-test` and `recomp-live`, read server-side from WEBSITE_SITE_NAME. Each environment keeps its own connections and keys; TEST sign-ins are not copied to LIVE. Diagnostic routes remain TEST-only.

Connection settings and encrypted sign-ins are stored under App Service HOME/data/external-connections, outside wwwroot, using exclusive file locks and atomic writes. This storage needs no new database tables or privileges. Fitness measurements remain in the existing SQL database. Keep this directory and the App Service Data Protection key ring in backups; losing either requires reconnecting. The store is isolated from the provider adapter and can be replaced with a database implementation later.

Connecting initially uses a 20-minute owner-bound preview in server memory. Saving requires additional explicit consent and persists the selected person ID plus encrypted email, provider password hash and token in the durable connection store. The plaintext password is never persisted. ASP.NET Data Protection binds the ciphertext to user ID, client ID and provider. App Service's default persistent Data Protection key ring must remain available across deployments; losing keys requires reconnecting. No credentials are shown in Administration. Provider HTTP logging is disabled because tokens appear in query strings.

Opening Daily Entry makes one antiforgery-protected background POST to check the owner's opted-in scale connection. Requests within the configured minimum interval are skipped (default 15 minutes); The Daily Entry “Pull scale readings” button and Device integrations “Sync now” bypass this interval. A successful import refreshes the view if the user has not begun editing; otherwise it shows a refresh notice. There is no timer or Always On requirement. Expired sessions trigger one login using the saved encrypted password hash. Changed credentials require reconnecting. Disconnect clears the saved sign-in and preserves imported measurements. A durable connection lease prevents concurrent imports.


Imports use the client's time zone and active program, preserve manual measurement days, and retain provider record IDs to skip repeats. Editing imported body measurements in Daily Entry creates a separate manual override; saving unrelated daily fields keeps an unchanged device reading intact. Imported records are not deleted if subsequently removed at the provider. Body-fat and subcutaneous-fat percentages become fractions; `rosm` and `vwc` percentages become skeletal-muscle and body-water pounds. These mappings match the user's verified Fitdays screenshot and existing manually recorded values. Generic `rom` is not substituted for skeletal muscle. Administration can disable body composition or configure mass units for future imports; existing imported records are preserved.

Protocol source: https://github.com/roquerodrigo/fitdays-api (MIT). Login: POST api/users/login; sync: POST api/sync/syncFromServer. Date bounds use start_time newest and end_time oldest. Regional redirects are bounded and allowlisted; responses are limited to 2MB. Settings allow history of 1–90 days and sync interval of 15–1440 minutes. This community-documented protocol can change upstream.
